# `detective` module

The rest of this repository is **preventative** — it stops bad configurations
from existing. This module is the other half: it records what actually happened,
so an incident can be reconstructed and a drifted account can be noticed.

| Control | Answers |
|---------|---------|
| **CloudTrail** | Who called which API, from where, when |
| **GuardDuty** | Is something behaving like an attacker right now |
| **AWS Config** | What did this resource look like last Tuesday, and what changed |
| **Security Hub** | How do we score against a published benchmark |

All of it lands in one KMS-encrypted, versioned, access-logged S3 bucket.

## Design notes

### Log file validation is the point of CloudTrail

`enable_log_file_validation = true` makes CloudTrail write signed digest files.
Without it, an attacker with S3 write access can edit the audit log and you
cannot tell. A trail that can be silently rewritten is not evidence.

The trail is multi-region with `include_global_service_events` — IAM, STS, and
CloudFront only emit into a multi-region trail, and those are exactly the calls
you care about during an incident.

It ships to **both** S3 and CloudWatch Logs. S3 is durable, cheap retention;
CloudWatch is what you alarm on in near real time rather than waiting for the
next S3 delivery. That dual path also satisfies Checkov `CKV2_AWS_10`.

### Account-global singletons

CloudTrail is *not* a singleton — an account can hold several trails, so every
environment can run its own safely.

GuardDuty, Config, and Security Hub **are** one-per-account-per-region. If dev
and prod target the same AWS account, enabling them from both root modules makes
the second `apply` fail. Hence the per-service toggles: this repo enables them
in prod and leaves them off in dev, the same pattern already used for the
account-global OIDC provider.

In a real multi-account setup, each account enables all four.

The log bucket, its access-log bucket, and the KMS key are created whenever the
module is instantiated, regardless of the per-service toggles. Keeping them
unconditional lets Checkov's graph link each bucket to its versioning,
encryption, and public-access-block resources — behind a `count` those links
break and the scan reports false negatives. If an environment wants none of
this, put `count = 0` on the module block rather than disabling every service.

### Two buckets, on purpose

Both buckets are SSE-KMS under the same customer-managed key, with S3 Bucket
Keys enabled — server-access-log delivery to a CMK-encrypted destination
requires the bucket key, and the key policy grants `logging.s3.amazonaws.com`
the `GenerateDataKey` it needs.

The access-log bucket does not log to itself. That would recurse, which makes it
the one Checkov skip in this module that is a law of the universe rather than a
judgement call.

## Cost

This is the module that actually costs money at rest:

| Service | Rough cost |
|---------|-----------|
| CloudTrail | First management-events trail is free; ~\$2/100k events after |
| GuardDuty | Usage-based; often ~\$5–30/mo on a small account |
| AWS Config | ~\$0.003 per configuration item recorded — the usual surprise on a busy account |
| Security Hub | ~\$0.0010 per check per month, plus per-finding ingestion |
| S3 + KMS | Storage plus \$1/mo per key |

`all_supported = true` on the Config recorder is thorough and is the line item
most likely to surprise you. Narrow the recording group if the bill matters more
than the completeness.

## Usage

```hcl
module "detective" {
  source = "../../modules/detective"

  name_prefix = module.tags.name_prefix

  enable_cloudtrail = true
  # Account-global: on in prod, off in dev when they share one AWS account.
  enable_guardduty    = true
  enable_config       = true
  enable_security_hub = true

  log_retention_days  = 365
  log_expiration_days = 365
}
```
